# Hearth Clinic

A starter monorepo for a homeopathic clinic management system. The Angular application contains the clinic dashboard, patient list, structured case-taking form, appointment list, and consultation workspace. The Spring Boot API provides JWT authentication, patient records, scheduling, consultation notes, remedy lookup, prescription history, invoice issuance, and dashboard aggregates.

This is an implementation foundation, not a production-ready or clinically validated system. It is not a substitute for clinical judgment, and it does not claim compliance with HIPAA, GDPR, local medical-record laws, or payment regulations. Do not enter real patient information until a qualified security/privacy review, deployment hardening, and applicable legal review are complete.

## Structure

- `backend/`: Java 17+, Spring Boot, Spring Security, JPA, Flyway, PostgreSQL.
- `frontend/`: Angular standalone application, TypeScript, RxJS, Angular Material, responsive SCSS.
- `docker-compose.yml`: local PostgreSQL only; no application containers.
- `render.yaml`: Render deployment Blueprint for the frontend, API, and managed PostgreSQL.

## Requirements

- Java 17 or later.
- Maven 3.9 or later.
- Node.js 20.19+ and npm 10+ (this scaffold was created with Node 24 and npm 11).
- Docker with Compose, or a locally running PostgreSQL 16 database.

## Local setup

Start PostgreSQL:

```sh
docker compose up -d db
```

Set backend environment variables in the shell. Generate a random 32-byte JWT key and Base64-encode it; never commit the resulting value:

```sh
export DATABASE_URL='jdbc:postgresql://localhost:5432/homeoclinic'
export DATABASE_USERNAME='clinic_app'
export DATABASE_PASSWORD='replace-with-a-local-secret'
export JWT_SECRET="$(openssl rand -base64 32)"
export BOOTSTRAP_DOCTOR_ENABLED=true
export BOOTSTRAP_DOCTOR_EMAIL='doctor@example.test'
export BOOTSTRAP_DOCTOR_PASSWORD='replace-with-at-least-14-characters'
```

Start the API from `backend/`:

```sh
cd backend
mvn spring-boot:run
```

Flyway creates the schema on startup. The bootstrap account is created only when explicitly enabled and does not overwrite an existing account. Disable `BOOTSTRAP_DOCTOR_ENABLED` after provisioning. Staff and patient accounts must be provisioned through an audited administrative workflow; public registration is intentionally absent.

In another terminal, start the Angular app:

```sh
cd frontend
npm install
npm start
```

Open `http://localhost:4200`. The Angular development server proxies `/api` to `http://localhost:8080`. Sign-in requires the provisioned doctor account. Production hosting must configure HTTPS, trusted origins, API routing, and secret injection.

## Public demo deployment on Render

This Blueprint is configured for **demo/test data only**. Do not use it for real patient records. The application still needs a formal security/privacy and regulatory review, independent audit logging, secure token lifecycle, backup/restore validation, operational monitoring, and production incident procedures before health data is hosted.

1. Push this repository to a private GitHub repository and create a Render account.
2. In Render, choose **New > Blueprint**, connect the repository, and deploy `render.yaml`. The Blueprint creates a static frontend, a Docker-based Spring API, and a managed PostgreSQL instance in the same region. The database is not exposed as a public service.
3. During setup, set `BOOTSTRAP_DOCTOR_EMAIL` to the clinic admin email and `BOOTSTRAP_DOCTOR_PASSWORD` to a unique password of at least 14 characters. Enter the password only into Render's secret environment-variable field, not in source control or chat. `JWT_SECRET` is generated by Render.
4. The initial static/API hostnames in `render.yaml` are `hearth-clinic.onrender.com` and `homeoclinic-api.onrender.com`. If Render assigns different hostnames, set `API_BASE_URL` on the static site to the API's HTTPS URL, set `FRONTEND_ORIGIN` on the API to the static site's exact HTTPS origin, and redeploy both services.
5. Wait for the API health check at `/actuator/health` to pass, then open the static site's HTTPS URL and sign in with the provisioned admin doctor credentials.
6. After the first admin has been created, disable `BOOTSTRAP_DOCTOR_ENABLED` in the API environment and redeploy. Create individual doctor logins in the Doctors section; never share one account across clinicians.

The frontend bundle is public by design; patient data and API operations must remain behind authentication. Render free/demo services may sleep or have limited availability. Review Render's current service, database retention, region, networking, and billing terms before deploying.

## API overview

All routes are under `/api/v1`; all except login require a bearer access token.

| Method | Route | Access | Purpose |
|---|---|---|---|
| POST | `/auth/login` | Public | Authenticate and issue short-lived JWT |
| GET, POST | `/doctors` | Doctor | List doctor accounts and create an individual doctor login |
| GET, POST | `/patients` | Doctor, staff | Search and create patients |
| GET, PUT | `/patients/{id}` | Doctor, staff | Read and update a patient/case record |
| GET | `/patients/me` | Patient | Read the account-linked patient profile |
| GET, POST | `/appointments` | Doctor, staff | List within a date range and book a slot |
| POST | `/appointments/{id}/consultations` | Doctor | Start a consultation |
| POST | `/consultations` | Doctor | Start or resume a walk-in consultation with `{ "patientId": "…" }`, no appointment required |
| PUT | `/consultations/{id}/notes` | Doctor | Save running and Hering's observation notes |
| POST | `/consultations/{id}/close` | Doctor | Complete a consultation and appointment; completed records are read-only |
| GET | `/patients/{id}/consultations` | Doctor | Consultation history |
| POST | `/consultations/{id}/prescriptions` | Doctor | Create a multi-remedy prescription |
| GET | `/patients/{id}/prescriptions` | Doctor | Chronological prescription history |
| GET | `/remedies` | Doctor, staff | List active remedies and stock |
| POST | `/remedies` | Doctor | Add a remedy and opening stock count |
| POST | `/invoices/appointments/{id}` | Doctor, staff | Issue one invoice for a visit |
| GET | `/dashboard` | Doctor, staff | Daily appointment, online pending, and invoice totals |

Consultations transition from `IN_PROGRESS` to `COMPLETED` when the doctor closes the visit. The dashboard shows currently open consultations, their status, elapsed start time, and a doctor-only close action, along with the number completed today.

The clinic admin doctor can create additional doctor accounts through `/doctors`. The first active doctor is promoted to admin by migration V4; newly created doctors are standard doctor accounts and cannot see or manage the Doctors page. Each account has a unique email and password hash. Set a distinct initial password of at least 14 characters for each colleague and share it through a private channel; the application never returns passwords or hashes. Existing users should sign out and back in once after V4 is applied so their session receives the admin flag. The Remedies menu remains available to doctors and staff.

## Important implementation gaps

- Appointment booking and invoice issuance are API-backed. The calendar UI currently displays today's list; booking controls, calendar navigation, payment collection/status transitions, invoice PDF generation, and invoice history UI remain to be implemented.
- The online video call provider is still a placeholder; no video call is initiated by this application.
- Remedy inventory supports listing and doctor-created remedy entries/opening counts. Lot/expiry tracking, dispensing, stock movement audit, and safe decrement-on-dispense behavior are not implemented.
- The patient profile page is available to linked `PATIENT` accounts; patient-side appointment/history screens and the audited account-to-patient linking workflow remain to be implemented.
- JWT access tokens are kept in browser `sessionStorage` in this starter. Production should use a reviewed token lifecycle, refresh/revocation strategy, stronger session protections, rate limiting, audit logging, and ideally an HttpOnly secure-cookie design where appropriate.
- Add automated backend integration tests, frontend tests, database backups/restore drills, monitoring, retention/deletion workflows, consent controls, and accessibility review before deployment.

## Security notes

Use TLS everywhere outside local development, least-privilege database credentials, secrets from a managed secret store, encrypted backups and storage, security headers, rate limits, audit records for access and changes, and a data-processing/privacy review. The current `JWT_SECRET` must be Base64 for at least 32 random bytes. Never use demo data as real clinical guidance; remedy choices and dosing must be determined by a qualified clinician.
